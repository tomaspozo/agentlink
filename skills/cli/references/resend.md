# Resend setup (transactional email)

Resend powers all outbound email in an Agent Link project. Two consumers
depend on it:

- **Auth SMTP** — Supabase's built-in mailer (signup confirmation, password
  reset, magic link) routed through Resend's SMTP, plus the `_hook_send_email`
  auth hook.
- **Transactional edge functions** — `internal-invite-member`,
  `internal-approval-decision`, `internal-send-auth-email`, etc., which call
  Resend directly and read `RESEND_API_KEY` / `RESEND_FROM_EMAIL`.

`npx agentlink-sh@latest resend setup` wires both in one command.

## The model: per environment

Resend is configured **per cloud environment** (`dev`, `prod`), mirroring how
Supabase credentials are per-env. There are two pieces, split by secrecy:

| Piece | Secret? | Lives in | Source of truth |
|-------|---------|----------|-----------------|
| **FROM address** (`Name <email>`) | No | `agentlink.json` → `cloud.environments.<env>.resend.fromEmail` | ✅ this file |
| **API key** (`re_…`) | Yes | the env's Supabase edge-function secret store | the secret store |

Key consequences:

- **Editing `agentlink.json`'s `fromEmail` by hand is supported** — it's the
  source of truth. `resend setup --env <env> --non-interactive` reads the FROM
  from there and pushes it. (It does **not** read `.env.local`.)
- **The API key is never in git or `.env.local`** as the source — only in each
  project's secret store. It's **sticky**: a command that doesn't pass
  `--api-key` leaves it untouched.
- **`local` has no Resend config.** Local dev sends through the **resend-box**
  sandbox (`RESEND_BASE_URL=http://host.docker.internal:4657`), which ignores
  the API key — so a fake/placeholder key locally is fine. Only cloud envs get
  real Resend wiring.

`.env.local`'s `RESEND_*` lines are a **derived local-runtime artifact** (for
`supabase functions serve` + resend-box), regenerated by `resend setup` for the
active env. `env use` does **not** rewrite them.

## Command — use flags, not positionals

```bash
resend setup --env <env> [--api-key <key>] [--email "Name <email@domain>"] [--name <display>] [--yes] [--non-interactive]
```

| Flag | Effect |
|------|--------|
| `--env <name>` | Target env, or `all`. Defaults to `cloud.default`; prompts if 2+ and unset. |
| `--api-key <key>` | **Rotates** the key. Absent ⇒ key untouched (sticky). |
| `--email <from>` | Sets the FROM. Bare email or `Name <email>`. Absent ⇒ keeps the env's current FROM. |
| `--name <display>` | Display name composed with a bare `--email`. |
| `--yes` | Confirms reusing the existing key when `--email` changes domains (non-interactive). |
| `--non-interactive` | Errors instead of prompting. |

> The positional form `resend setup <api_key> <from_email> [from_name]` is
> **deprecated** and will be removed next release. It also confused ordering
> (the first positional must be the `re_…` key, not the email). Always use flags.

## Resolution rules

**First time for an env** (no `resend` block yet) — account and FROM domain are
coupled (the domain must be verified under the key's account), so it's
**all-or-nothing**:

- Pass **both** `--api-key` and `--email`, **or**
- Pass **neither** → uses the saved default account (`resend defaults`), or
  prompts interactively.
- Passing only one → error.

**Already configured** — the key is **sticky**:

- `--email` / `--name` alone → change the FROM, key untouched (partial push).
- Same-domain FROM change → applied silently.
- **Different-domain** FROM change without `--api-key` → requires confirmation
  (`--yes`, or an interactive prompt), since the current key may not cover the
  new domain.
- `--api-key` alone → rotates the key (warns to ensure the new account has the
  FROM domain verified).

## Recipes

**Change only the display name** (e.g. `AgentLink Demos` → `Requester`, same
address):

```bash
resend setup --env prod --email "Requester <apps@demos.emails.agentlink.sh>"
```

or edit `agentlink.json` → `cloud.environments.prod.resend.fromEmail`, then:

```bash
resend setup --env prod --non-interactive
```

Both keep the API key sticky and re-assert edge secrets + Auth SMTP.

**Rotate the API key:**

```bash
resend setup --env prod --api-key re_new_key_here
```

**Promote dev → prod with a brand-new account:**

```bash
resend setup --env prod --api-key re_xxx --email "App <hello@yourdomain.com>"
```

**Re-assert after a manual dashboard edit** (idempotent force-push):

```bash
resend setup --env prod --non-interactive
```

## Debugging "email not sending"

There is **no `check` flag** for Resend (it was removed when Resend went
per-env). Verify instead:

1. `agentlink.json` → does `cloud.environments.<env>.resend` exist? If not, run
   `resend setup --env <env>`.
2. Does the env's secret store contain `RESEND_API_KEY`? If the manifest has the
   block but the secret is gone, re-run `resend setup --env <env>` to re-push.
3. Both green → check Supabase edge-function logs (usual culprit: FROM domain
   not verified under that key's account), the `pgmq.q_agentlink_tasks` queue,
   and the `_hook_send_email` auth-hook URI.

## Saved default account

`resend defaults show` / `resend defaults clear` manage a user-level default
Resend account (`~/.config/agentlink/credentials.json`) — purely a convenience
so first-time setup of a new env can reuse the same key + FROM without
re-typing. It is **not** a source of truth for any project.
